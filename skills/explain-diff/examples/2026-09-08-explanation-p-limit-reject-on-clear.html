rejectOnClear in p-limit

How commit 8907801f gives clearQueue() a way to settle the promises it throws away, and why that had to be an opt-in.

Fixes issue #25 · Add `rejectOnClear` option · 5 files, 79 insertions, 10 deletions · sindresorhus/p-limit, MIT

Before this commit, calling limit.clearQueue() discarded the queued calls and left their promises unresolved forever. An await Promise.all(...) over those promises never returned. This commit adds a rejectOnClear option that rejects them with an AbortError instead, and the interesting part is what the queue had to become for that to be possible.

1. Background

The smallest mental model

p-limit runs async functions with a cap on how many are in flight. You create a limiter with a concurrency, then wrap each call:

import pLimit from 'p-limit';

const limit = pLimit(2);

const results = await Promise.all([
  limit(() => fetchUser(1)),
  limit(() => fetchUser(2)),
  limit(() => fetchUser(3)),   // waits until one of the first two finishes
]);

limit(fn) returns a promise immediately, whether or not fn has started. That promise is the caller's only handle on the call. Everything in this change is about what that promise does when the call it represents is thrown away.

Definition

Pending vs active. A call is active once fn has been invoked; limit.activeCount counts those. A call is pending while it is still sitting in the queue waiting for a slot; limit.pendingCount is the queue's size. clearQueue() only ever touches pending calls. It has never cancelled an active one, and this commit does not change that.

What already existed

The limiter before the commit is about ninety lines. Four functions do the work, and one of them is stranger than it looks:

const queue = new Queue();          // yocto-queue, O(1) enqueue/dequeue
let activeCount = 0;

const resumeNext = () => {
  if (activeCount < concurrency && queue.size > 0) {
    activeCount++;
    queue.dequeue()();              // the queued value IS a function
  }
};

const next = () => {
  activeCount--;
  resumeNext();
};

const enqueue = (function_, resolve, arguments_) => {
  // Queue the internal resolve function instead of the run function
  // to preserve the asynchronous execution context.
  new Promise(internalResolve => {
    queue.enqueue(internalResolve);
  }).then(run.bind(undefined, function_, resolve, arguments_));

  if (activeCount < concurrency) {
    resumeNext();
  }
};

const generator = (function_, ...arguments_) => new Promise(resolve => {
  enqueue(function_, resolve, arguments_);
});

Read enqueue twice. What goes into the queue is not the task and not run. It is internalResolve, the resolver of a throwaway promise whose only job is to have .then(run) attached to it. Calling that resolver schedules run as a microtask rather than invoking it inline, which is what the comment means by preserving the asynchronous execution context: a task never starts synchronously inside the limit() call that queued it.

The behaviour this commit is about

clearQueue: {
  value() {
    queue.clear();
  },
},

queue.clear() drops every internalResolve on the floor. Nothing is left holding a reference to those resolvers, so the throwaway promises never resolve, run is never scheduled, and the promise the caller got back from limit(fn) is never settled by anybody. It is not rejected. It is not resolved. It is garbage that a running await is still waiting on.

Consequence

The documented use for clearQueue() is teardown: discard work that references state your app is about to throw away. But the idiomatic way to use p-limit is await Promise.all(promises), and Promise.all settles only when every input settles. Teardown and the idiom were mutually exclusive. That is issue #25.

2. Intuition

There are two promises per call, and only one of them is reachable

Every limit(fn) creates a pair:

The outer promise

Returned to the caller. Its resolve is passed down into enqueue and stored in the closure of the pending run.

new Promise((resolve) => {
  enqueue(function_, resolve, args);
})

This is the promise your await is attached to.

The gate promise

Internal, never returned. Its resolver is the value in the queue; resolving it is what lets the task start.

new Promise(internalResolve => {
  queue.enqueue(internalResolve);
}).then(run)

This is the thing queue.clear() destroys.

Clearing the queue kills the gate. The outer promise is a separate object, and after the clear nothing in the program holds its resolve in a form that will ever be called. So the fix is not about the queue's contents being dropped, it is about the queue not carrying enough information: to settle the outer promise on the way out, clearQueue needs the outer reject.

The queue stops holding functions and starts holding items

Before

queue.enqueue(internalResolve)
// ...
queue.dequeue()()

One callable. Start it, or lose it.

After

queue.enqueue({run, reject})
// ...
queue.dequeue().run()
// or
queue.dequeue().reject(abortError)

Two ways to retire an entry, and both settle the caller's promise.

Why it is an option and not the new behaviour

Code that clears a queue today and never touches the discarded promises is correct today. Make the clear reject unconditionally and that same code gains rejections nobody handles, which in Node is a process-level warning or, with --unhandled-rejections=strict, a crash. So the behaviour ships behind rejectOnClear, defaulting to false, and the docs point the reader at the case that actually needs it: you await the promises.

3. Code

All application code is in index.js; the types in index.d.ts and one test in test.js. Ordered here by the path a value takes, not by file.

3.1 Reading the option, and the shape of the argument

index.js

export default function pLimit(concurrency) {
  let rejectOnClear = false;

  if (typeof concurrency === 'object') {
    ({concurrency, rejectOnClear = false} = concurrency);
  }

  validateConcurrency(concurrency);

  if (typeof rejectOnClear !== 'boolean') {
    throw new TypeError('Expected `rejectOnClear` to be a boolean');
  }

The options-object form already existed and pulled out one field. It becomes a destructuring assignment with a default, which is the whole of the parsing change. Note the parameter is still named concurrency and is reassigned in place, so the identifier means a number from this point on regardless of which call form was used.

The type check is separate from validateConcurrency and throws eagerly, at construction. A limiter with a mistyped option never exists, so no caller ever waits on a promise governed by a misread flag.

3.2 The queue item

index.js

const enqueue = (function_, resolve, reject, arguments_) => {
  const queueItem = {reject};

  // Queue the internal resolve function instead of the run function
  // to preserve the asynchronous execution context.
  new Promise(internalResolve => {
    queueItem.run = internalResolve;
    queue.enqueue(queueItem);
  }).then(run.bind(undefined, function_, resolve, arguments_));

  if (activeCount < concurrency) {
    resumeNext();
  }
};

The object is built before the promise, then run is attached inside the executor and the object is enqueued. Order matters and it is safe here: a Promise executor runs synchronously, so by the time enqueue returns the item in the queue has both fields. Nothing can observe a half-built item, because the only two consumers are resumeNext and clearQueue, and neither can run in the middle of a synchronous executor.

index.js — the two consumers

 const resumeNext = () => {
   if (activeCount < concurrency && queue.size > 0) {
     activeCount++;
-    queue.dequeue()();
+    queue.dequeue().run();
   }
 };

run is still internalResolve, so the microtask hop is unchanged and tasks still never start synchronously.

3.3 Carrying reject down from the caller

index.js

-const generator = (function_, ...arguments_) => new Promise(resolve => {
-  enqueue(function_, resolve, arguments_);
+const generator = (function_, ...arguments_) => new Promise((resolve, reject) => {
+  enqueue(function_, resolve, reject, arguments_);
 });

This is the line that makes the outer promise reachable from the queue. resolve continues to travel into run's bound arguments; reject stops at the queue item.

3.4 Clearing

index.js

clearQueue: {
  value() {
    if (!rejectOnClear) {
      queue.clear();
      return;
    }

    const abortError = AbortSignal.abort().reason;

    while (queue.size > 0) {
      queue.dequeue().reject(abortError);
    }
  },
},

Two things to notice.

The disabled path is the old body, returning early. Existing users get the identical code path they had, not a new one that happens to behave the same, which is the cheapest possible answer to "did this change break the default?".

The enabled path drains rather than clearing. It needs each item on the way past to call its reject, and dequeue in a loop is the one operation that both empties the queue and hands over the items. pendingCount is queue.size, so it reads 0 synchronously after either path, which is what the test asserts.

Where the error comes from

AbortSignal.abort() returns a signal that is already aborted, and its reason is the platform's standard abort error: a DOMException with name === 'AbortError'. Reading it off a throwaway signal costs one line and no dependency, and produces the same object shape fetch rejects with, so a caller can use one err.name === 'AbortError' check across both. It is not an Error subclass in the instanceof sense, so match on name, not on class.

One error instance is created per clearQueue() call and shared by every rejected promise in that clear. Callers get identity-equal reasons for calls discarded together, and the stack on it points at the abort machinery rather than at any one task.

3.5 The bug the option would have had in limitFunction

index.js

 export function limitFunction(function_, options) {
-  const {concurrency} = options;
-  const limit = pLimit(concurrency);
+  const limit = pLimit(options);

   return (...arguments_) => limit(() => function_(...arguments_));
 }

limitFunction takes the same options object and used to extract a single field from it, which would have silently dropped rejectOnClear the moment anyone passed it. Forwarding the object instead makes the new option work here for free, and works only because pLimit already accepts that form.

3.6 The test

test.js

test('clearQueue rejects pending promises when enabled', async t => {
  const limit = pLimit({concurrency: 1, rejectOnClear: true});

  const runningPromise = limit(() => delay(100));
  const pendingPromiseOne = limit(() => delay(10));
  const pendingPromiseTwo = limit(() => delay(10));

  await Promise.resolve();
  t.is(limit.pendingCount, 2);

  limit.clearQueue();
  t.is(limit.pendingCount, 0);

  await runningPromise;
  await t.throwsAsync(pendingPromiseOne, {name: 'AbortError'});
  await t.throwsAsync(pendingPromiseTwo, {name: 'AbortError'});
});

The await Promise.resolve() is not decoration. The first call's task starts on a microtask, so pendingCount is 3 synchronously and 2 only after the microtask queue has turned once. The assertion pins the state the test is actually about.

await runningPromise then states the other half of the contract: the active task was not cancelled, it completed, and its promise resolved normally in the same clear that rejected its two queued siblings.

3.7 Types, and one consequence found later

index.d.ts adds readonly rejectOnClear?: boolean to Options and documents the rejection under clearQueue. The published docs recommend it for the Promise.all case rather than describing it neutrally, which is the honest framing: if you do not await the promises, the old silence was never a problem.

A later commit, f3e7f9ba ("Fix limitFunction queue clearing"), shows what 3.5 half-finished. Forwarding the options made rejectOnClear reach the limiter, but the function limitFunction returns is a bare arrow with no clearQueue on it, so there was no way to trigger the clear through that API at all:

const limitedFunction = (...arguments_) => limit(() => function_(...arguments_));
Object.defineProperty(limitedFunction, 'clearQueue', {
  value: limit.clearQueue,
});

return limitedFunction;

with the return type widened to ((...arguments_: Arguments) => Promise<ReturnType>) & Pick<LimitFunction, 'clearQueue'>. Worth reading as a pair: accepting an option is not the same as exposing the operation the option modifies.

3.8 What still does not happen

  • Active tasks are untouched. No AbortSignal is handed to task functions, so a running fetch keeps going and its promise settles on its own result.
  • Rejections are yours to handle. Turning the option on and then ignoring the promises trades a hang for an unhandled rejection. The default stays false for exactly that reason.
  • No per-call opt-in. The flag lives on the limiter, decided at construction, and cannot vary between calls into the same limiter.
